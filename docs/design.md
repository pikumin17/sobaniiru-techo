# そばにいる手帳＋犬猫性格診断ページ 設計書

- **対象発注書**：`spec-v2.md`（2026-11-14 作成、全文を確認済み）
- **前提**：ビルドなしの静的サイト、サーバーなし、IndexedDB保存、スマホ優先のPWA。
- **判断ポイントの扱い**：発注書にない仕様判断は【判断ポイント】として分け、推奨案を添えました。日数・文字サイズなどの数値はすべて設計上の提案値で、調査に基づく事実ではありません。

## 0. 先に決めてほしいこと（発注者の判断が必要な3点）

1. **公開後の数字の測り方**（発注書§9）
   - サーバーなし・端末内保存のままでは、「アプリの登録数」「1週間後に続けている割合」を発注者側から数えられません。
   - 推奨は、Cookieを使わない匿名のアクセス解析を1つだけ入れ、イベントの回数だけを送ることです。対象イベントは、ページ表示、診断完了、シェアボタン押下、ペット登録完了、記録保存です。
   - 記録の中身、ペット名、診断の回答は送りません。
   - 入れる場合は、設定画面の「このアプリについて」に何を数えているかを明記します。入れない場合、§9の数字のうちアプリ側の2つは測れません。
2. **日数の初期値**
   - 削除した記録を元に戻せる期間は、30日を推奨します。
   - 書き出しを促すまでの期間は、7日を推奨します。
3. **緊急連絡先メモの持ち方**
   - 発注書ではPDFに入れる項目ですが、ペット登録の項目にはありません。
   - 推奨は、設定に全体で1つの自由記入メモとして持つことです（端末内のみ）。

## 2. データモデル

### 2.1 IndexedDBの構成

- DB名は `senior-care-techo`（仮名に合わせた仮の名前）です。
- 外部ライブラリは使わず、薄い自作ラッパー（`idb.js`）で扱います。
- IDはすべて `crypto.randomUUID()` で作ります。端末をまたいで読み込んでも衝突しません。
- 日付は端末のローカル日付の文字列（`YYYY-MM-DD`）、日時はISO 8601文字列で持ちます。

| ストア | キー | インデックス | 用途 |
|---|---|---|---|
| `pets` | `id` | ― | ペット |
| `records` | `id` | `[petId+date]`、`date` | 毎日の記録 |
| `schedules` | `id` | `petId` | 投薬・通院の予定 |
| `doses` | `id` | `[petId+date]`、`scheduleId` | 投薬チェックの実績 |
| `customItems` | `id` | ― | カスタム記録項目 |
| `settings` | `key` | ― | 設定（キーと値） |
| `trash` | `id` | `expiresAt` | 削除したデータの復元用 |

### 2.2 各レコードのフィールド

**pets（ペット）**

| フィールド | 型 | 説明 |
|---|---|---|
| `id` | string | UUID |
| `name` | string | 名前（必須） |
| `species` | `"dog"` / `"cat"` | 犬か猫か（必須） |
| `birthYear` / `birthMonth` / `birthDay` | number / null | 生年月日。不明ならすべて null |
| `conditionsMemo` | string | 持病メモ（自由記入） |
| `clinicMemo` | string | かかりつけ病院メモ（自由記入） |
| `color` | string | 誤認防止用のテーマ色（登録順に自動で割り当て、変更可） |
| `order` | number | 並び順 |
| `createdAt` / `updatedAt` | string | 日時 |

- 【判断ポイント】生年月日は「年だけ分かる」保護犬・保護猫を想定し、年・月・日を別々に持つ案を推奨します。
- 【判断ポイント】登録時に入力した体重は、`pets` に持たず、その日の体重の記録として `records` に保存する案を推奨します。体重の置き場が1か所になり、グラフと食い違いません。ペット画面には最新の体重の記録を表示します。

**records（記録）**：1回の入力が1レコードです。1日に何回でも付けられます。

| フィールド | 型 | 説明 |
|---|---|---|
| `id` | string | UUID |
| `petId` | string | 対象のペット |
| `date` / `time` | string | 記録の日付と時刻（初期値は現在。変更可） |
| `meal` | `"all"` / `"half"` / `"little"` / `"none"` / null | 食事量（全部・半分・少し・食べない） |
| `water` | string / null | 水（選択肢は下の判断ポイント） |
| `pee` | string / null | おしっこ |
| `poop` | string / null | うんち |
| `poopState` | string / null | うんちの状態 |
| `weightKg` | number / null | 体重 |
| `note` | string | 睡眠や様子のメモ |
| `custom` | object | `{ カスタム項目ID: 値 }` |
| `batchId` | string / null | 一括入力で同時に作った記録の目印 |
| `createdAt` / `updatedAt` | string | 日時 |

- 付けなかった項目は null とし、「記録なし」と「食べない」を区別します。
- 【判断ポイント】発注書は水と排泄の選択肢を定めていません。推奨は次のとおりです。
  - 水：多い／ふつう／少ない／飲まない
  - おしっこ：あり／なし
  - うんち：あり／なし
  - うんちの状態：ふつう／かたい／やわらかい／水っぽい
- どれも飼い主が見たままを選ぶ言葉にとどめ、病名や症状名に見える語は使いません。

**schedules（投薬・通院の予定）**

| フィールド | 型 | 説明 |
|---|---|---|
| `id` / `petId` | string | |
| `kind` | `"med"` / `"visit"` | 投薬か通院か |
| `title` | string | 薬の名前、または通院の用件（自由記入） |
| `memo` | string | 自由記入メモ |
| `slots` | array | 投薬のみ。`[{ key, label, time }]`（例：label「朝」、time は目安の時刻で空でも可） |
| `repeat` | object | 投薬のみ。`{ type: "daily" / "weekly" / "once", weekdays: [] }` |
| `startDate` / `endDate` | string / null | 投薬の期間（終了日なしも可） |
| `visitDate` / `visitTime` | string / null | 通院のみ |
| `placeMemo` | string | 通院のみ。場所のメモ |
| `createdAt` / `updatedAt` | string | |

- 薬の名前や量は、入力候補や自動補完を一切出しません（§8）。
- 【判断ポイント】くり返しは「毎日・曜日指定・1回だけ」の3種を推奨します。「○日おき」は次の版の候補とします。

**doses（投薬チェックの実績）**

| フィールド | 型 | 説明 |
|---|---|---|
| `id` | string | `予定ID_日付_slotのkey`（同じ枠を二重に記録しない） |
| `scheduleId` / `petId` / `date` / `slotKey` | string | |
| `doneAt` | string | チェックした日時 |
| `titleSnapshot` / `slotLabelSnapshot` | string | チェック時点の薬の名前と枠の名前 |

- 「まだの投薬」は、今日の予定の枠から `doses` にあるものを引いて求めます。
- チェックを外すと、その行を消します。もう一度1タップで戻せるので、ごみ箱には入れません。
- 予定を後から直しても、過去の実績は控えた名前で表示できます。

**customItems（カスタム記録項目）**

| フィールド | 型 | 説明 |
|---|---|---|
| `id` | string | |
| `label` | string | 項目名（例：床ずれのケア、歩行の様子） |
| `type` | `"check"` / `"choice"` / `"number"` / `"text"` | チェック・選択・数値・メモ |
| `choices` | string[] | 選択式のときの選択肢 |
| `unit` | string | 数値のときの単位（任意） |
| `petIds` | string[] / null | 対象の子。null は全員 |
| `order` | number | 並び順 |
| `hidden` | boolean | 非表示（削除の代わり） |
| `createdAt` / `updatedAt` | string | |

**settings（設定）**：`{ key, value }` の形で持ちます。

| key | 内容 |
|---|---|
| `currentPetId` | いま選んでいる子 |
| `fontScale` | 文字サイズ（標準・大・特大） |
| `emergencyMemo` | 緊急連絡先メモ（自由記入、端末内のみ） |
| `lastExportAt` | 最後に書き出した日時 |
| `exportNudgeSnoozedUntil` | 書き出しの促しを「あとで」にした期限 |
| `persistResult` | `persist()` の結果 |
| `onboardingDone` | はじめに画面を済ませたか |

**trash（削除済みデータの復元用）**

| フィールド | 型 | 説明 |
|---|---|---|
| `id` | string | |
| `kind` | `"record"` / `"schedule"` / `"pet"` | 何を消したか |
| `label` | string | 一覧に出す説明（例：「11/14 モモの記録」） |
| `payload` | object | `{ ストア名: [元のレコードそのまま] }` |
| `deletedAt` / `expiresAt` | string | 削除日時と保存期限 |

- 削除は「元のストアから消す」と「`trash` に入れる」を1つのトランザクションで行います。
- ペットを消すときは、その子の記録・予定・投薬実績をまとめて1件の `payload` に入れ、「元に戻す」で全部戻します。
- 期限切れの分は、アプリ起動時に消します。
- 【判断ポイント】各レコードに削除フラグを立てる方式もあります。ただし一覧やグラフのすべての読み出しで除外が必要になり、漏れると消した記録が見えてしまいます。そのため、別ストアに移す方式を推奨します。

### 2.3 バージョン管理とマイグレーション方針

バージョンは2つあり、同じ番号をそろえて上げます。

- **DBバージョン**：IndexedDBの整数バージョン。
- **書き出し形式バージョン**：JSONの `formatVersion`。

方針は次のとおりです。

1. `migrations.js` に「v1→v2」「v2→v3」の関数を順番に並べます。`onupgradeneeded` の中で、古いバージョンから1段ずつ適用します。
2. 変更は足す方向を原則とします。フィールドの追加は、読み出し側で既定値を補います。ストアの削除やフィールドの意味の変更は、最小版の期間中は行いません。
3. バージョン更新のトランザクションは、途中で失敗すると全体が取り消されて元のデータが残ります。この性質を使い、移行処理はすべてこのトランザクションの中で完結させます。
4. 失敗したときは、データに触らずにエラー画面（§9）を出します。
5. 古い形式のJSONを読み込むときも、同じ移行関数を通してから保存します。
6. アプリより新しい形式のJSONは読み込まず、「アプリを最新にしてから読み込んでください」と表示します。
7. 別のタブが古い版を開いたままだと更新が止まるので、`blocked` と `versionchange` を拾います。「ほかのタブを閉じてください」と表示します。
8. Service Workerで新しい版を取得しても、入力中に勝手に再読み込みしません。ホームに「新しい版があります［更新する］」を出します。
9. テストとして、各バージョンの見本JSON（`tests/fixtures/`）を保存しておきます。「旧版のデータ→最新版へ移行→件数と内容が一致」を、リリースのたびに確認します。

## 3. 記録入力の設計

### 3.1 1画面の構成（A2）

上から順に、次のように並べます。項目は大きな選択ボタンで、1タップで選べます。もう一度押すと選択を解除できます。

1. **対象ペットの帯**（上部に固定、§3.3）
2. 日付と時刻（初期値は現在。タップで変更）
3. 食事量：全部／半分／少し／食べない
4. 水
5. おしっこ／うんち／うんちの状態（うんち「あり」のときだけ状態を出す）
6. 投薬：今日の予定の枠をチェック式で表示（`doses` に保存。ホームの「あげた」と同じデータ）
7. 体重（数値キーボード）
8. カスタム項目
9. 睡眠や様子のメモ
10. 「保存する」（下部に固定）。修正のときは「削除する」も表示

- 保存の完了は、トランザクションの完了を待ってから「保存しました」と表示します。
- 入力途中で画面を離れようとしたら、「保存していない入力があります」と確認します。

### 3.2 複数ペットの一括入力

- 対象ペットの帯に「ほかの子にも同じ記録を付ける」ボタンを置きます。押すと登録済みの子の名前が並び、複数選べます。
- 一括のあいだ、帯には「3匹に記録：モモ・ソラ・ハナ」のように全員の名前を出します（名前は例）。
- 保存ボタンも「3匹ぶん保存する」に変わります。
- 保存すると、選んだ子ごとに1件ずつ記録を作り、同じ `batchId` を付けます。後の修正と削除は1匹ずつです。
- 体重と投薬チェックは子ごとに違うので、一括のあいだは入力欄を閉じます。「体重と投薬は1匹ずつ記録します」と表示します。
- 保存後は「モモ・ソラ・ハナに保存しました［取り消す］」を出し、一括の押し間違いをすぐ戻せるようにします。
- 【判断ポイント】一括の保存前に確認画面をはさむ案もあります。タップが増えるので、ボタンの文言で頭数を示す方式と「取り消す」の組み合わせを推奨します。

### 3.3 対象ペットの誤認防止

- 記録入力の最上部に、ペットのテーマ色の帯を固定表示します。内容は「いま記録中：モモ（犬）」で、名前は画面でいちばん大きい文字にします。スクロールしても消えません。
- 色に加えて、犬・猫の絵と名前の文字を必ず併記します。
- 「保存する」ボタンにも名前を入れます（「モモの記録を保存する」）。
- 保存後の表示にも名前を入れます（「モモに保存しました」）。
- ホーム・ふりかえり・予定でも、上部のペット切り替えで選択中の子を同じ色と大きさで示します。
- 入力途中で子を切り替えようとしたら、「入力中の内容はソラの記録になります。よろしいですか」と確認します。
- 1匹だけの家庭では切り替えは出しませんが、名前の帯は出します。

### 3.4 カスタム項目

- 追加は設定の「記録項目の管理」（A9）と、記録入力の末尾の「＋項目を追加」の両方からできます。
- 入力するのは、項目名、種類（チェック・選択・数値・メモ）、対象の子（全員か特定の子）です。
- 項目は削除ではなく「非表示」にします。過去の記録の値は残り、ふりかえりと申し送りで読めます。
- 【判断ポイント】最小版では、標準項目（食事・水など）の非表示や並べ替えは対象外とすることを推奨します。
- 項目のひな型（「床ずれのケア」などの候補）は、発注書の例の範囲にとどめ、ケア方法の助言に見える候補は出しません。

## 4. 画面内リマインドの設計

### 4.1 出す場所と内容

ホーム（A1）の最上部に「今日の予定」カードを置きます。アプリを開いたときに最初に目に入る位置です。

- **まだの投薬**：今日の予定の枠のうち、チェックのないもの。表示は、子の名前、薬の名前、枠の名前、目安の時刻、大きな「あげた」ボタンです。
- **済んだ投薬**：チェック済みの枠。薄く表示し、「取り消す」で外せます。
- **通院の予定**：今日の予定と、近い日の予定です。
- 複数の子がいる場合は、選択中の子に限らず全員分を、子ごとにまとめて出します。
- 予定が何もない日は、カードを小さくして「今日の予定はありません」と表示します。

補足の方針です。

- 目安の時刻を過ぎた未チェックの枠は、「まだ」の文字と枠線で目立たせます（色だけに頼りません）。
- 日付をまたいでアプリを開いたままの場合に備え、画面に戻ったとき（`visibilitychange`）に今日の日付を取り直します。
- 【判断ポイント】通院は「今日から7日先まで」を出す案を推奨します。
- 【判断ポイント】前日以前の未チェックはホームに積み上げず、ふりかえりで確認できれば足りるとする案を推奨します。積み上がると本当の今日の予定が埋もれます。

### 4.2 注意文言の置き場

文言は発注書のとおり「時刻になっても通知は出ません。スマホのアラームと併用してください」とし、言い換えません。

| 置き場 | 出し方 |
|---|---|
| 予定の登録・編集（A5）の時刻欄のすぐ下 | 常に表示。時刻を入れる瞬間に目に入る |
| 予定一覧（A4）の上部 | 常に表示 |
| ホームの「今日の予定」カードの下端 | 常に表示（本文と同じ大きさ） |
| はじめに（A0） | 初回に1度 |

- 時刻の入力欄のラベルは「目安の時刻」とし、「通知時刻」「アラーム」という語は使いません。
- ブラウザの通知許可は求めません。

## 5. 申し送りPDFの方式

### 5.1 方式

- 申し送り（A7）で対象の子と期間を選ぶと、同じ画面の下に印刷用の表示が出ます。
- 「印刷・PDFにする」ボタンで `window.print()` を呼び、端末の印刷画面からPDFとして保存・共有してもらいます。
- PDF生成ライブラリは使いません。印刷用の体裁は `print.css`（`@media print`、`@page` でA4縦）で整えます。
- ボタンの近くに「印刷画面で『PDFとして保存』や『共有』を選んでください」と手順を書きます。
- 期間は「過去7日・14日・30日・日付を指定」から選びます（【判断ポイント】選択肢は提案値です）。
- 【判断ポイント】スマホのブラウザやホーム画面に追加した状態では、印刷画面からPDFにする手順が機種ごとに違います。実機（iPhone・Android）で確認し、機種別の手順をREADMEと画面の説明に反映する必要があります。
- 印刷が使えない環境に備え、同じ内容を画面で見せて渡せるようにし、JSON書き出しも案内します。

### 5.2 レイアウトと含める情報（1匹につき1部）

| 順 | ブロック | 内容 |
|---|---|---|
| 1 | 見出し | 「申し送り」、子の名前、犬か猫か、対象期間、作成日 |
| 2 | 基本情報 | 生年月日（不明なら「不明」）、最新の体重の記録とその日付、持病メモ、かかりつけ病院メモ |
| 3 | 緊急連絡先メモ | 設定のメモをそのまま（入れるかどうかを作成時に選べる） |
| 4 | 投薬・通院の予定 | 現在有効な予定：名前、枠と目安の時刻、くり返し、メモ |
| 5 | 記録の表 | 1日1行〜複数行。列は、日付と時刻／食事／水／おしっこ／うんちと状態／投薬（済んだ枠）／体重／カスタム項目／メモ |
| 6 | 体重のグラフ | 期間内に体重の記録が2件以上あるときだけ |
| 7 | 末尾の注意書き | 「この書類は飼い主による記録です。体調の判断は必ず獣医師へ」 |

- 印刷は白黒でも読めるようにします。食事量は色ではなく文字で書き、表の行は改ページで分断されないようにします（`break-inside: avoid`）。
- 記録をそのまま並べるだけにし、「食欲が落ちています」のような要約や評価の文は自動で作りません（§8）。
- 緊急連絡先メモは渡す相手によって不要な場合があるので、作成時のチェックで外せます。初期値は「入れる」です。

## 6. JSON書き出し／読み込みの設計

### 6.1 形式

```json
{
  "app": "senior-care-techo",
  "formatVersion": 1,
  "exportedAt": "（書き出した日時）",
  "counts": { "pets": 0, "records": 0, "schedules": 0, "doses": 0, "customItems": 0, "trash": 0 },
  "data": {
    "pets": [], "records": [], "schedules": [], "doses": [],
    "customItems": [], "settings": [], "trash": []
  }
}
```

- 7つのストアをすべて含めます。ごみ箱と設定も入るので、「書き出し→全削除→読み込み」で元通りになります。
- ファイル名は `senior-care-techo-backup-YYYYMMDD-HHmm.json` です。
- 共有メニューが使える端末では「共有する」（Web Share APIのファイル共有）も出し、使えない端末ではダウンロードにします。
- 【判断ポイント】ホーム画面に追加した状態でのファイル保存の挙動は、機種ごとに実機確認が必要です。

### 6.2 置き場と、最終書き出し日の表示・促し

- 設定（A8）の最上部に「バックアップ」の枠を置きます。内容は次のとおりです。
  - 「最後に書き出した日：○月○日（○日前）」。まだなら「まだ書き出していません」。
  - 大きな「データを書き出す」ボタン。
  - 「データを読み込む」ボタン。
  - 保存の保護状態（`persist()` の結果）。
- ホームには、最後の書き出しから7日を過ぎたら帯を出します（7日は§0の提案値）。文言は「最後の書き出しから○日たちました。機種変更や故障に備えて書き出しましょう」です。
- 帯のボタンは「いま書き出す」と「あとで」の2つです。「あとで」を押すと翌日まで出しません。
- 記録が1件もないうちは促しません。
- 全画面をふさぐ出し方はせず、記録の操作を邪魔しません。
- 「最後に書き出した日」は、書き出し操作をした日です。ファイルが実際に保存されたかまではアプリから確かめられません。そのため、文言は「書き出した日」にとどめます。

### 6.3 読み込みの流れ（A11）

1. ファイルを選びます。
2. 中身を検査します。見るのは、JSONとして読めるか、`app` が一致するか、`formatVersion` が扱える範囲か、必須フィールドがあるかです。
3. 要約を表示します。「書き出した日：○月○日／ペット○匹／記録○件／予定○件」と、いま端末にあるデータの件数を並べます。
4. 読み込み方を選びます。初期選択はどちらにも付けず、必ず選んでもらいます。
   - **追加する**：いまのデータを残し、ファイルにあって端末にないものだけを足します。
   - **上書きする**：いまのデータをすべて消して、ファイルの内容に置き換えます。
5. 上書きを選んだ場合は、もう1段の確認を出します。文言は「いまのデータ（ペット○匹・記録○件）はすべて消えます」です。その場に「先にいまのデータを書き出す」ボタンを置きます。
6. 1つのトランザクションで実行します。途中で失敗したら全体が取り消され、読み込み前の状態が残ります。
7. 結果を表示します。「追加○件、すでにあったので飛ばした○件」のように件数で示します。

- 【判断ポイント】「追加」で同じIDがあった場合は、端末側を残して飛ばす案を推奨します。更新日時の新しい方を採る案もありますが、気づかないうちに端末の記録が書き換わります。
- 設定（`settings`）は、「追加」では端末側を残し、「上書き」ではファイル側にします。

### 6.4 往復テスト（納品物4に対応）

`tests/roundtrip.html` で、次の順に自動で確認し、結果を画面に出します。

1. 見本データを投入する
2. 書き出す
3. 全ストアを消す
4. 読み込む（上書き）
5. もう一度書き出す
6. 手順2と手順5の `data` が一致することを確認する

### 7.6 スコア計算方式

- 5つの軸に2問ずつ割り当てます。
- 点数は、よくある＝2点、ときどき＝1点、あまりない＝0点です。各軸は0〜4点になります。
- 判定の順序は次のとおりです。
  1. 最高点の軸と最低点の軸の差が1点以下なら「バランス名人タイプ」。
  2. それ以外は、最高点の軸のタイプ。
  3. 最高点が同点の場合は、その軸の前半の質問（1〜5問目）の点が高い方。それでも同じなら質問番号の若い軸。
- 計算はすべてブラウザの中で行い、回答はどこにも送らず、保存もしません。
- 【判断ポイント】「差が1点以下ならバランス」というしきい値は提案値です。全回答パターンは3の10乗通りなので、`tests/quiz-distribution.html` で総当たりし、タイプの偏りを確認してから確定することを推奨します。偏りが大きければ、しきい値か同点時の規則を調整します。

### 7.7 シェア文とシェア画像

**シェア文**（ひな型）

> うちの犬は「いつでも全力！冒険家タイプ」でした🐶
> 犬の性格タイプ診断（無料・登録不要）
> #犬の性格タイプ診断
> （タイプ別ページのURL）

- 猫は「うちの猫は」「#猫の性格タイプ診断」に替えます。
- 共有メニューが使える端末では「シェアする」（Web Share API）を出します。あわせて「Xでシェア」「LINEで送る」「文章をコピー」のボタンを置きます。
- 【判断ポイント】XとLINEの共有用URLの形式は、実装時に各社の公式の最新仕様を確認します。

**シェア画像**

- **リンクのプレビュー用**
  - タイプごとの静的ページ（Q3）を12枚用意します。
  - それぞれに、事前に作った画像を `og:image` として指定します。
  - プレビューを作るクローラーはJavaScriptを実行しない前提で考える必要があります。そのため、結果をURLのパラメータで出し分ける方式ではなく、タイプ別の静的HTMLにします。
- **保存・送信用**
  - 結果画面で、Canvasにタイプ名・短い説明・診断名・URLを描いて画像にします。
  - 「画像を保存」または共有メニューで渡します。外部のサーバーは使いません。
- 画像の絵柄は、イラストか図形と文字で作ります。他者の写真やキャラクターは使いません。
- 【判断ポイント】画像の大きさは、リンクのプレビューでよく使われる横長（1200×630）を推奨します。
- 【判断ポイント】結果画面でペットの名前を任意で入力し、画像に入れる案があります。入れる場合は、名前はその画面の中だけで使い、URLにも保存先にも残しません。最小版では、名前なしを推奨します。

### 7.8 アプリへの控えめな導線

- 結果画面のいちばん下、シェアと「もう一度」の後ろに、小さな枠を1つだけ置きます。
- 文言案は次のとおりです。

> シニアになったら、毎日の様子をこれで記録。
> そばにいる手帳 ― 無料・登録不要 ［見てみる］

- ポップアップや、結果を見る前の誘導は行いません。
- 自社アプリへの案内だけで、他社の商品への誘導、広告、アフィリエイトは入れません。

## 8. 禁止事項の反映箇所

| 禁止事項（発注書§4） | 反映箇所 |
|---|---|
| 病名・薬・量の判断や提案をしない | 薬の名前とメモは自由記入のみ。入力候補・自動補完・薬の一覧を持たない。記録の値に対する評価、警告、色による「異常」表示、しきい値の判定を作らない。グラフに「正常範囲」の帯を描かない。申し送りに自動の要約文を入れない。AI相談・チャット機能は作らない |
| 「体調の判断は必ず獣医師へ」の表示 | ①ホームの下端に常に表示。②ふりかえりのグラフのすぐ下。③申し送りの末尾（印刷にも入る）。④はじめに（A0）。⑤設定の「このアプリについて」。文言は発注書のとおりで統一する |
| 「心理師」「カウンセリング」などを使わない | アプリと診断の全文言を `messages.ja.js` と診断のデータファイルに集める。禁止語の一覧（心理師、カウンセリング、カウンセラー、セラピー、治療、診療、処方 など）で検索する確認をリリース前の手順に入れる。診断の説明文で「心理テスト」「心理分析」も使わない |
| 広告・アフィリエイトを入れない | 外部の広告タグ、アフィリエイトリンク、商品紹介を入れない。外部への読み込みは§0-1の解析のみ（入れる場合） |
| 住所・電話番号・位置情報を集めない | 住所・電話の専用入力欄を作らない。位置情報のAPIを呼ばない。緊急連絡先とかかりつけ病院は自由記入メモだけで、端末の外へ送らない。メモ欄の下に「この内容は端末の中だけに保存されます」と表示する |
| 診断を病気診断に見せない | 名前を「性格タイプ診断」とし、「おたのしみ用」と明記。入口と結果の下に「この診断はおたのしみ用です。健康状態や病気を判定するものではありません」と表示。健康に関わる質問を入れない。結果に点数や「危険度」「要注意」などを出さない。配色や絵柄を医療風（白衣、聴診器、カルテ）にしない |
| 「うちの子手帳」を使わない | 表示名は「そばにいる手帳」。名前は `messages.ja.js`、`manifest.webmanifest`、各HTMLの `<title>` の3か所だけに置き、後で一括で変えられるようにする |

【判断ポイント】「体調の判断は必ず獣医師へ」を全画面に常に出す案もあります。文字が大きい前提では入力の場所を圧迫するので、上の5か所を推奨します。

## 9. エラー表示の方針

### 9.1 共通の方針

- すべて日本語で、次の3点を書きます。
  1. 何が起きたか
  2. データはどうなったか
  3. 次に何をすればよいか
- 英語のエラー名や内部の詳細は、「くわしい情報」を開いたときだけ見せます。問い合わせのときに伝えられます。
- 文言は `messages.ja.js` に集めます。
- 保存の成功は、トランザクションの完了を確認してから表示します。失敗したときは入力内容を画面に残し、「もう一度保存する」を出します。
- 想定外のエラー（`error`、`unhandledrejection`）も拾います。そのときは「うまく動きませんでした。記録は消えていません。画面を開き直してください」という帯を出します。
- 文字だけで伝わるようにし、色や絵だけの表示にしません。自動で消える表示は、エラーには使いません。

### 9.2 主な場面と文言の方向性

| 場面 | 表示の内容 |
|---|---|
| 保存に失敗 | 「保存できませんでした。入力した内容は画面に残っています。もう一度『保存する』を押してください」 |
| 端末の空き容量が足りない | 「端末の空きが足りず保存できませんでした。先にデータを書き出してから、端末の空きを増やしてください」 |
| 端末内の保存が使えない（プライベートブラウズなど） | 「このブラウザの設定では記録を保存できません。通常の画面で開き直してください」 |
| 読み込んだファイルが違う・壊れている | 「このファイルは読み込めませんでした。いまのデータは変わっていません」 |
| ファイルの形式がアプリより新しい | 「このファイルは新しい版で作られています。アプリを最新にしてから読み込んでください。いまのデータは変わっていません」 |
| 更新時のデータ移行に失敗 | 「アプリの更新に失敗しました。記録は消えていません。画面を開き直してください」 |
| ほかのタブが開いていて更新できない | 「このアプリをほかのタブでも開いています。ほかのタブを閉じてください」 |
| 保存の保護（`persist()`）が認められなかった | エラーではなく注意として設定に表示：「端末の空きが少なくなると、記録が消える可能性があります。こまめな書き出しをおすすめします」 |
| 印刷・共有が使えない | 「この端末では印刷画面を開けませんでした」と、代わりの方法の案内 |

### 9.3 データ消失対策チェックリストへの対応

| チェック項目（発注書§5） | 設計上の対応 | 確認方法 |
|---|---|---|
| 端末内に保存され、再起動しても残る | すべてIndexedDBに保存（§2）。保存完了の確認後に成功を表示 | 記録→ブラウザを終了→開き直して残っていることを実機で確認 |
| `persist()` を呼ぶ | 最初のペット登録の保存時に呼ぶ。結果を `settings` に保存し、設定に表示。認められなかった場合は、起動時に再度試す | 設定の表示と、開発者ツールでの確認 |
| JSONの往復で全データが元通り | 全ストアを書き出しに含める（§6.1） | `tests/roundtrip.html`（§6.4） |
| 読み込み前に上書きか追加かを確認 | 読み込みの確認画面（§6.3）。上書きは二段階の確認 | 画面のスクリーンショットと手動テスト |
| 削除の前に確認画面 | 記録・予定・ペット・ごみ箱を空にする操作のすべてで確認。ペットの削除は、消える件数を表示 | 手動テストとスクリーンショット |
| マイグレーションでデータが消えない | §2.3（1段ずつの移行、失敗時は全体取り消し、足す方向の変更のみ） | 旧版の見本データからの移行テスト（`tests/migrations.html`） |

- 加えて、削除後は「削除しました［元に戻す］」を表示し、ごみ箱（A10）から期限内はいつでも戻せます。
- 【判断ポイント】ブラウザによっては、長く使っていないサイトの端末内データを消す場合があります。iPhoneのSafariについては、ホーム画面に追加していないサイトで期間による消去があると理解していますが、条件は変わりうるので、実装時にWebKitの最新の公式情報で確認が必要です。対策として、はじめに画面と設定で「ホーム画面に追加」を案内し、書き出しの促し（§6.2）を合わせて行うことを推奨します。

## 10. 実装の分割（ファイル構成の案）

### 10.1 前提

- ビルドなしです。ブラウザ標準のESモジュール（`<script type="module">`）で分割します。
- 外部のCDNやライブラリには依存しません。IndexedDBは自作の薄いラッパー、グラフはSVGを自前で描き、PDFは印刷ビューです。
- フォルダをそのまま静的ホスティングに置けば動きます。
- ESモジュールは `file://` では動かないので、手元で動かすときは簡易の静的サーバーを使います。この手順はREADMEに書きます。
- 【判断ポイント】発注書§6は例としてReact・Vite・Dexieを挙げつつ「任せる」としています。今回はビルドなしの前提に合わせて、素のJavaScriptを採ります。画面数が少なく、依存の更新による不具合（発注書§2の不満の1つ）も避けられます。

### 10.3 補足

- アプリと診断は同じサイトの別フォルダに置きます。Service Workerの範囲は `/app/` だけにし、診断ページには影響させません。

  - 同じ内容を表でも見られるようにします。
- 作る順序の推奨は次のとおりです。データ消失対策を先に固めます。
  1. DB層と往復テスト
  2. ペット登録
  3. 記録入力とホーム
  4. 予定とリマインド
  5. ふりかえり
  6. 申し送り
  7. ごみ箱とカスタム項目
  8. PWA化
  9. 診断ページ
  10. 実機確認とスクリーンショット
- 診断ページはアプリと依存関係がないので、並行して作れます。
- 納品物3のスクリーンショット（ホーム、ペット登録、記録、リマインド、削除確認、設定、エラー表示）は、A1・A6・A2・A1の予定カード・確認ダイアログ・A8・§9.2の各画面に対応します。
